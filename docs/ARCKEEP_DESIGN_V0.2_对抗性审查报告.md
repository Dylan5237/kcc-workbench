# 对抗性审查报告：ARCKEEP_DESIGN_V0.2.md

- 审查对象：`docs/ARCKEEP_DESIGN_V0.2.md`（状态：设计定稿 · 待开发，2026-08-27）
- 审查基准：`PRODUCT_DESIGN_PHILOSOPHY.md`（哲学）、`HIGH_LEVEL_DESIGN_V0.1.md`（v0.2 继承的骨架与未决问题）、品牌交付 v1.0（`docs/brand/`）、v1 代码级对抗性审查报告（RT 系列，作为工程教训证据库）
- 审查方式：只读文档审查，不修改被审文档。四个视角独立攻击后融合：资深全栈工程师（E）/ 产品设计（P）/ 心理学（H）/ UX 专家（U），附安全（S）与战略注记
- 严重度分级：BLOCKER（开发前必须回答，否则必然返工）/ HIGH（影响核心承诺）/ MED（影响质量与规模）/ LOW（注记）

---

## A. 裁决

**REVISE** —— 信息架构与克制边界是合格的好设计，但"用户确认链路"这一产品核心承诺在全文档最薄：5 个 BLOCKER 全部集中在"系统生成 → 用户确认 → 成为当前认知 → 进入下一次会话"这条链上。以现状直接开工，最先烂掉的恰好是产品哲学里最引以为傲的部分（来源可追溯、用户有最终确认权）。

## C. 发现清单（按严重度排序）

### DR-01【BLOCKER】上下文勾选面板——全程 stakes 最高的交互，规格只有半句话（U/E）

- 位置：§3.1「点击"开始" → 弹出上下文勾选面板（默认最小相关），确认后进入接入态」
- 论据：这个面板是产品哲学 §6「更好地忘记」和 v0.1 §10.4「先看索引，再按需读取」的唯一执行点。哲学用了整整两节讲相关性分寸（东坡肉例子、重要性≠相关性），落地文档只有「默认最小相关」五个字。未定义的包括：可选上下文的内容形态（文件？关键判断？会话片段？）、默认集的判定规则、token 预算、选错的后果（错误上下文进入 agent 会直接污染产出，且产出会回流成为"最近产出"）。对比：同文档给"分叉节点虚线半透明"写了完整边界（§3.2），给真正影响结果的面板只写了半句。
- 建议：开发前补一节规格——面板信息结构、默认集规则、每项的来源标注（延续"系统推测/你确认"语义）、超预算提示。这是 v0.2 与哲学文档之间最大的落差。

### DR-02【BLOCKER】确认链路没有闭环：摘要谁确认、在哪里确认、确认负荷多少，全无规格（U/H/P）

- 位置：§4.2 SessionNode.summary「由用户确认」、§4.1 currentStatus「只能由用户确认或改写」、§3.3「会话结束事件同时更新最近产出」、§3.4「点击后触发摘要回流」
- 论据：文档处处说"你确认"，但没有一处定义确认动作本身：(a) agent 会话结束后系统生成摘要，它在界面上以什么形态等待确认？项目空间没有"待确认"区域，Session Map 的 tentative 节点没有确认入口（§3.2 只定义了点击看详情）；(b) 确认的量级没有预算——每次会话结束一条摘要、每条关键判断一次确认、状态每次更新一次确认，高频仪式的必然结果是 alert fatigue：第 50 次确认时用户无脑点过，"已确认"与"系统推测"的区分随之失效，§4.3 的整个来源追溯体系建立在用户真的在读这个前提上；(c) 推测条目的处置路径缺失——猜错了怎么办，忽略、删除、点过之后的状态，都没有定义。
- 建议：定义"收件箱"式的统一确认队列（数量可见、可批量、可跳过且跳过后推测自动过期而非永久悬挂），并为确认动作设定负荷上限（如每次回流最多 2 条待确认）。这是 DR 系列里唯一同时被三个视角独立命中的问题。

### DR-03【BLOCKER】「会话结束事件」的检测机制未定义，产品闭环的最后一步没有主人（E/P）

- 位置：§5.3「增加：会话结束事件触发回流、文件变化与会话关联」、§3.4「用户点击后触发摘要回流 + 产出刷新」
- 论据：v1 已验收的是"会话 API 目录解析"——被动读。v0.2 要的是事件——主动推。两者之间有真实的工程质变：嵌入 WebContentsView 里的 agent 会话何时算"结束"？轮询 session API 的状态字段？用户直接关窗口算不算结束（此时 WebContentsView 已销毁，事件从哪来）？进程崩溃呢？文档没有 fallback 设计。产品层面同样裸露：§3.4 把回流挂在"会话结束 · 回到项目"按钮上，依赖用户记得点——而用户在接入态的注意力全部在 agent 原生界面里，侧轨是被 peripheral 的。检测未定义 + 按钮可能被遗忘，闭环两个触发源都不可靠。
- 建议：定义三级触发——会话 API 状态轮询（有 API 的 agent）→ 窗口/进程生命周期事件（兜底）→ 手动按钮（最终手段）；明确任一路径触发都走同一回流管道，并在侧轨显示"检测到会话已结束，待接回"状态。

### DR-04【BLOCKER】「携带上下文进入 agent」的注入通道未定义（E）

- 位置：§5.1 最小共同要求「接收相关项目上下文的方式」、§3.4 侧轨「携带上下文 2 项」、§3.1 接续点 → 开始
- 论据：文档精确规定了上下文在 Arckeep 内部如何被选择（接续点、勾选面板），但没有规定它如何越过 agent 边界。Kimi Code Web 接受上下文的方式（URL 参数？注入输入框？会话模板？）未写；Claude Code / Codex 经 CloudCLI 的通道（CLI 参数？初始 prompt 文件？）未写；L1/L2 级 agent（§5.2）干脆没有通道。这直接决定 DR-01 的面板设计（选出的上下文以什么形态交付），也决定"从选中的经历继续"（§3.2）是不是一个可实现的承诺。
- 建议：为每个接入级别定义注入通道与降级形态（L4 结构化注入 / L3 初始消息 / L2 落到项目目录的上下文文件 / L1 仅登记），写进 §5 的协议表。

### DR-05【BLOCKER】Arckeep 自有数据的存储、写入与备份模型缺席（E）

- 位置：§4.1 数据模型、§4.3「数据与事实边界」
- 论据：§4.3 仔细规定了"不复制别人的事实"（文件以目录为准、Git 以仓库为准、会话以原生载体为准），但 currentStatus、nextItems、decisions、SessionNode 这些 Arckeep 自己拥有的事实——恰好是产品价值的核心——存哪、怎么写、如何防损坏、如何备份导出，零规格。哲学 §10 明确要求"个人记忆归用户所有，可以检查、纠正、导出和备份"；v0.2 没有兑现这个要求的任何机制。v1 的教训就发生在同类问题上：手写 TOML 补丁器产生重复节导致配置非法（RT-014），写入路径无测试（RT-013）。另注：Project.id = "本地目录路径的规范化形式"（§4.1），目录改名/移动/junction 即项目身份丢失，v0.1 §15.1 自己提过这个问题，v0.2 没有回答。
- 建议：补一节"工作站自有数据"：存储格式（建议单文件 JSONL 或 SQLite）、原子写入（tmp+rename，v1 已有此模式）、损坏恢复、导出备份入口；项目身份改为"目录路径 + 稳定 projectId 双键"，路径可变、ID 不变。

### DR-06【HIGH】D-18「不允许页面级滚动条」把一次用户抱怨固化成了设计宪法，溢出行为无规格（P/U）

- 位置：§2.3、D-18（依据：用户明确要求"别让我下滑"）
- 论据：用户对看板/流程原型的反感是真实信号，但"不滚动"是手段不是目的——目的是"第一眼看到全部重点"。固化为硬约束的后果：(a) 信息密度由布局预算决定而非任务决定，"最多显示 6 条"只对最近产出定义了（§3.1），待办 8 条、判断 5 条、产出 20 个文件时的截断/分页/省略规则全部缺失；(b) 只承诺 1920×1080 以上完整可见，1366×768 笔记本、125%/150% 系统缩放、窗口被拖小的行为未定义——无滚动 + 小窗口 = 内容被无声裁切；(c) 可访问性整体缺席：键盘导航、焦点态、屏幕阅读器、文本缩放在产品设计文档里零提及（品牌手册反而要求了 WCAG 2.2 AA，两份文档标准不一致）。
- 建议：D-18 改写为"首屏一屏内呈现核心判断所需信息，溢出走分页或'查看全部'而非页面滚动"；为每个列表定义溢出行为；补可访问性最小集（焦点可见、全键盘可达、对比度按品牌手册 AA）。

### DR-07【HIGH】推测与用户待办混排（D-16）存在内在的锚定矛盾（H/P）

- 位置：§1 D-16（依据：用户不希望被系统指挥）、§3.1 混排规格
- 论据：D-16 的逻辑是"分开展示 = 系统指令区，混排 = 平等"。但混排的实际心理效果相反：推测条目与用户意图获得同等的视觉权威和位置优先权，用户倾向于从"已列出的选项"中选择而非自己生成下一步——这是经典的锚定 + 默认效应。为了消除指令感而混排，反而让系统的声音更隐蔽地指挥。真正的解法不是视觉上的平等，而是**权力上的不对称**：推测可以被一键否决、有有效期、且明确标注猜错率。
- 建议：保留混排（视觉已被接受），但补三个机制：推测条目带"忽略"动作（且忽略行为回流改进推测）；推测有有效期（如 7 天未确认自动消失）；来源标注从灰色小字升级为可读句（"我猜的，来自昨天会话"）。

### DR-08【HIGH】默认落点跳过了 v0.1 自己留下的未决问题（P）

- 位置：§3.1「项目空间（默认落点）」、v0.1 §15.5「首页以最近项目、当前项目还是待继续工作为中心？」
- 论据：v0.2 直接默认落进"当前项目"的项目空间，但多项目用户回来时的第一个问题是"该继续哪项工作"，不是"这个项目继续什么"。左侧栏的项目列表按时间排序（原型如此），选择默认项目的规则（最近活跃？有待确认事项优先？）未定义。v0.1 明确说这个问题"不能在没有进一步探索时擅自替用户决定"，v0.2 在没有标注的情况下替它做了决定。
- 建议：补默认项目选择规则，或在多项目且有多个"值得继续"时增加一个轻量到达层。至少在文档中标注这是对 v0.1 §15.5 的临时回答。

### DR-09【HIGH】会话内容进入索引/摘要/快照时无敏感信息治理（S）

- 位置：§3.1 会话现场摘录、§4.2 summary、§3.3 时间机器（继承 v1 的快照含未跟踪文件全文）
- 论据：agent 会话内容可能包含代码、密钥、内部 URL。v0.2 设计层面对三类存储（会话索引与摘要、时间机器快照、诊断日志）只规定了日志不含 token（AGENTS.md 约束），摘要与快照的敏感信息策略未定义。v1 代码审查已证明这个应用的攻击面真实存在（RT-001 本地服务无认证、RT-007 从页面正文提取路径可被内容引导）。设计文档不解决实现，但应给出约束。
- 建议：设计层补一条约束：摘要在落库前经 secrets 模式过滤；时间机器快照沿用并明示文件类型白名单与淘汰窗口（v1 已有上限 20/40 的策略，文档应承接并写入 PRIVACY 承诺）。

### DR-10【MED】v1 已实跑发现的性能陷阱未被列为继承约束（E）

- 位置：§3.3「继承 v1 Viewer 的全部已验证能力」、§6 阶段 2
- 论据：v1 审查实跑发现：文件变更 1.8s 防抖后同步执行 git status/diff/ls-files 三连，大 monorepo 上冻结整个应用 UI（RT-010）；HTTP 处理器无全局兜底导致主进程级崩溃（RT-009）。"继承全部能力"如果没有同时继承"已知陷阱清单"，2.0/演进开发会把同样的坑再踩一遍——尤其在本仓库这种 669 个 node_modules 包 + 5 个 dist 输出目录的真实工作目录上，监听过滤策略（§4.1 artifacts「从文件系统读取」的成本模型）不是可选项。
- 建议：§6 阶段 2 的验收标准补两条：Viewer 服务移出主进程（utilityProcess 或 2.0 薄壳的独立线程）；监听与 git 调用的过滤/异步/排队约束。

### DR-11【MED】空态、错误态、降级态只覆盖了一屏（U）

- 位置：§3.1 有空态规格；§3.2/§3.3 无；§3.4 有降级文案但无视觉
- 论据：没有会话的 Session Map、没有产出的 Viewer、非 Git 目录的时间机器（v0.1 §15.1 明确问过"没有 Git 的任务如何形成项目"，v0.2 未回答）、agent 启动失败、会话 API 超时、工作目录被移动——全部无规格。设计哲学 §3 要求"快速恢复和深入追溯都要成立"，错误态恰是追溯最需要界面的时刻。
- 建议：为四屏各补最小空态/错误态文案与形态（可复用 §3.1 空态的引导文案模式）。

### DR-12【MED】Session Map 的时间轴形态没有规模设计（P）

- 位置：§3.2、§6 阶段 3「最小模型」
- 论据：5 个节点的横向时间轴成立，50 个节点（一个活跃项目 2 个月）即崩溃：横向空间、分叉悬挂、上下交替标签全部失效。无缩放、过滤、按阶段聚合的设想。§6 说"最小模型"可以先做，但 §8 验收标准没有规模用例，最小模型的边界（多少节点以内可用）没有定义，超过边界的产品行为（退化为列表？）没有 fallback。
- 建议：文档标注最小模型的规模假设（如 ≤20 节点），并指定退化形态（按周聚合 / 列表视图）作为规模超界时的安全网。

### DR-13【MED】「已取代判断」每日在场的损失厌恶成本（H）

- 位置：§3.1 关键判断含已取代条目、§2.2「已取代判断：浅褐底灰字标签」
- 论据："做第二个 Vibe Kanban——你后来主动否定"每天出现在项目空间。设计意图（历史不支配现在）正确且来自哲学 §5，但"可查"不等于"在场"。每天看到自己被否定的判断是持续的轻微自我对抗，长期会促使用户删除历史来逃避——那才是最坏结果（伪造始终正确的历史，哲学 §7 明令禁止）。
- 建议：已取代判断默认折叠为计数（"历史 1"），点击展开；保留可查，取消在场。

### DR-14【MED】currentStatus 的陈旧度没有反馈机制（H/P）

- 位置：§3.1 开场白、§4.1 currentStatus.updatedAt
- 论据：开场白是"回来第一眼"的 prospective memory 支持，方向正确。但它完全依赖状态的新鲜度：用户两周没更新，开场白就在以最高视觉权重展示过期事实。原型里有时间戳（好），但没有"这条状态可能已过期"的主动提示——陈旧状态比没有状态更误导。
- 建议：updatedAt 超过阈值（如 7 天）时，元信息行追加"可能需要更新"提示（延续品牌的披露语气：简短、非命令式）。

### DR-15【MED】接入态回流后，项目空间各区块的更新语义未定义（U/P）

- 位置：§3.3「会话结束事件同时更新项目空间的最近产出」、§3.4
- 论据：回流后"最近产出"自动刷新（定义了），但"可能值得继续的事"会不会因这次会话新增推测条目？"会话现场"立即替换还是等摘要确认？"关键判断"会不会出现新的待确认候选？四类信息的回流节奏不一致是可以接受的，但不定义就会出现"回来一看，有的更新了有的没有"的不一致感。
- 建议：定义回流后的区块更新矩阵（立即 / 待确认后 / 不自动）。

### DR-16【LOW】候选模块入口在视觉稿侧栏先行固化（S/P）

- 位置：视觉稿侧栏"候选"区（个人认知索引/能力与资源/额度总览）、§7 开发边界
- 论据：哲学 §12 和 v0.1 §9 都警告候选不得自动升级为模块。视觉稿把三个候选画成常驻入口，用户看到入口即产生期待——这是一种隐性的范围承诺。标注"未确认"缓解了问题但没有消除。

## D. 问题簇融合分析（单条是中危，成簇是产品级风险）

### 簇 1 · 信任链（DR-01 / DR-02 / DR-03 / DR-04 / DR-07）

产品的核心承诺是"系统可以推测，但用户有最终确认权，来源永远可追溯"。这条链上的每一环都有一个洞：上下文怎么进 agent（DR-04）→ 会话什么时候算结束（DR-03）→ 摘要在哪确认（DR-02）→ 推测错了怎么处置（DR-02/07）→ 上下文选错的后果（DR-01）。单独看每个都是"开发时再定也行"的细节；连起来看，是产品差异化价值（区别于"又一个 agent 启动器"）的全部所在。**建议作为开工前的第一优先级整体解决，而不是分散到各模块开发中顺手处理。**

### 簇 2 · 规模（DR-06 / DR-10 / DR-12）

"一屏呈现一切"（D-18）+"继承 v1 全部能力"（§3.3）+"最小模型"（§6）共同默认了小数据世界：少待办、少判断、少节点、小仓库。真实用户（本仓库就是例子：669 个依赖包、5 个构建输出目录、每天多次会话）会在 4-8 周内击穿所有三个假设。每个单点都有简单解法（分页/聚合/过滤），难的是承认"无滚动"是有适用边界的设计，而不是普适宪法。

### 簇 3 · 离开-返回闭环（DR-03 / DR-02 / DR-15）

"接入 ≠ 改造"（D-20）是本文最成熟的设计决策，但它的配套——离开 agent 后回到项目的闭环——没有主人。检测（DR-03）、确认（DR-02）、回流后各区块更新节奏（DR-15）三件小事共同决定"出去干活、回来归档"这个核心叙事是否成立。簇 1 解决前，接入态做得越顺，回流失败的对比越刺眼。

## E. 做对的、不应因本审查而改动的部分

对抗性审查的目的是找问题，不是推翻设计。以下决策经四个视角攻击后成立，应保留：

1. **§4.3 数据与事实边界**（不制造第二份事实）——罕见地诚实，从源头避免了一致性地狱；DR-05 要求的是补齐"自有事实"，不是动摇这条边界。
2. **D-20 接入 ≠ 改造**（大块原生 + 窄条侧轨）——正确地拒绝了"统一聊天界面"的诱惑，保住了各 agent 的原生能力和接入成本的可控性。
3. **D-21 分叉语义只显示不操作**——对未验证交互保持开放的正确姿势。
4. **§7 开发边界清单**——六个"不做"每一条都有哲学依据，是范围管理的范本。
5. **开场白 + 来源标注的信息层级**（§3.1 结构本身）——"先当前状态和下一步，再逐层追溯"忠实落地了 v0.1 §10。
6. **§8 验收 8 问**——可检验、非主观，是设计文档验收的应有形态。
