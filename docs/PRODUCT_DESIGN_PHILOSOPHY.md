# Arckeep 产品设计哲学

> 状态：产品探索阶段的设计原则  
> 更新日期：2026-08-26  
> 产品名：`Arckeep`（2026-08-27 正式确定）  
> 说明：本文用于判断产品方向，不是 PRD、路线图或功能清单。仓库名、应用包名和发布标识的迁移另行决定。

## 1. 我们想做的是什么

Arckeep 想成为用户自己的**长期工作环境**，而不是把多个 Agent 页面拼在一起的启动器。

Agent 和 harness 会不断变化。今天可能使用 Codex、Kimi Code、Claude Code、Cursor、DSH，明天也会出现新的选择。工作站不应依附其中任何一个，而应让用户的项目、历史、产出和个人积累跨越这些变化持续存在。

我们的核心追求是：

> **让工作连续，让进步复利。**

用户每次回来，都能准确地继续工作；每一次工作，也都能成为下一次更好的起点。

## 2. 工作是中心，Agent 是可替换的工具

工作站首先回答的不是“今天要打开哪个 Agent”，而是“今天要继续哪项工作”。进入项目以后，再选择适合当前任务的 Agent。

**通俗例子：**

用户昨天在 Claude Code 中完成了需求分析，今天想让 Codex 继续实现。正常体验不应该是重新配置目录、复制上下文、解释项目背景，而应该是打开同一个项目，选择 Codex 接着做。换的是工具，不是工作现场。

**设计含义：**

- 产品以项目和工作为中心，不以某个 Agent 的会话列表为中心。
- 不强迫所有 Agent 变成相同界面，也不抹掉它们各自的优势。
- 工作站统一的是工作连续性，而不是强行统一所有工具。

## 3. 让工作连续，而不只是让会话连续

一段聊天可以结束，但项目不会因此结束。用户重新进入项目时，需要恢复完整的工作状态：目标、进度、最近产出、待办、关键判断，以及上一次会话现场。

**通俗例子：**

用户周五下班前让 Agent 做到一半，周一回来时不应该先翻几十页聊天记录。工作站应帮助他迅速看清：现在做到哪里、刚刚生成了什么、还有什么没完成、为什么采用当前方案，以及从哪里继续最合适。

**设计含义：**

- 会话是项目经历的一部分，不是项目本身。
- 摘要不能代替原始现场；快速恢复和深入追溯都要成立。
- 判断一个能力是否重要，首先看它能否帮助用户更快、更准确地继续工作。

## 4. 让每次工作成为下一次的基础

好的产品不只让用户今天完成得更快，还应让用户、项目和协作方式持续进步。一次产出不应散失，一次探索不应白费，一次纠正也不应在换会话或换 Agent 后归零。

**通俗例子：**

用户已经多次纠正 Agent：“健康检查通过不等于业务验收完成。”以后无论换成哪个 Agent，在汇报交付状态时都应想起这条教训，而不是再次把服务能访问误报成产品已经验收。

**设计含义：**

- 保存的不只是结果，也包括值得复用的判断和经验。
- 不同 Agent 应能继承已经确认的合作经验。
- 产品要帮助用户形成更好的判断和方法，而不是只增加产量、制造依赖。

## 5. 历史完整保留，但不能支配现在

过去的信息可能在未来重新产生价值，因此不应被粗暴删除。但保存一段历史，不等于让它持续影响当前任务。

> **历史可追溯，当前认知可识别，来源可解释，载体可更换。**

**通俗例子：**

项目最初决定采用方案 A，后来因为真实运行问题改成方案 B。系统应保留当初选择 A 的背景，也要清楚标明现在采用 B，以及是谁、在哪次会话、基于什么证据作出了改变。新 Agent 默认按照 B 工作，但复盘时仍能找到 A。

**设计含义：**

- 当前结论和历史结论必须能够区分。
- 重要判断应知道来自哪里、适用于什么范围。
- 更换 Agent 或会话载体，不应切断项目的演进历史。

## 6. 更好地忘记：相关经验出现，无关历史沉默

记忆的目标不是让 Agent 知道得越来越多，而是让它在正确的场景想起正确的信息。信息可以一直存在，但没有被当前任务需要时，应当保持沉默。

为了让用户和 Agent 都容易理解，个人记忆可以按内容分成五种视角：**我是谁（identity）**、**我如何判断（principles）**、**我希望怎样协作（preferences）**、**我当前处于什么环境（context）**、**我积累了哪些经验与方法（knowledge）**。这五类适合作为记忆地图，但不应成为互斥的硬目录：同一条信息可能同时具有内容类型、适用范围、稳定程度、当前状态和来源。

**通俗例子：**

用户让 Agent 做番茄炒蛋。系统可以想起“用户不喜欢太甜”，但不能因为用户上周做过东坡肉，就擅自在番茄炒蛋里加入东坡肉。东坡肉不是错误信息，只是与当前任务无关。

同样，GitHub 操作规范在准备提交代码时很重要，在讨论菜谱时就不应出现。

**设计含义：**

- 保存信息和调用信息是两件事。
- 工作站不仅要管理记忆，还要管理记忆在当前任务中的“发言权”。
- 完整加载全部历史不是能力强，而是缺乏分寸。
- Agent 应先看简明索引，判断哪些内容可能相关，再按需读取正文，而不是每次扫描整个记忆库。
- 记忆本身的重要程度不能代替与当前任务的相关程度；高层身份信息也可能与眼前工作无关。
- 当前项目的目标、进度和待办应由项目工作现场负责，不能仅靠个人记忆中的 `context` 副本维持。

## 7. 可以学习，但不能擅自立法

系统需要区分三种东西：一次发生过的经历、尚未确认的暂时理解、用户明确确认的稳定习惯。

> **经历可以留下，经验需要谨慎提炼，规则不能擅自确立。**

记忆“讲的是什么”和“现在处于什么状态”必须分开。`preference` 描述内容类型，不代表它已经成为稳定偏好；`principle` 也不能仅凭 Agent 归类就自动拥有最高权威。任何从经历升级为经验、技能或原则的过程，都必须保留依据，并让用户拥有最终确认权。

**通俗例子：**

用户某次赶时间，说“回答短一点”。系统可以记录这次要求，但不能据此认定用户永远只喜欢简短回答。如果用户在多次开放讨论中都要求“不要过早下结论”，系统可以形成一个有范围的暂时理解：用户在开放探索场景中偏好保持问题开放；但不能把它扩展到故障诊断和明确执行任务。

**设计含义：**

- 单次指正不能自动升级为永久规则。
- 宁可偶尔让用户再次提醒，也不能错误固化一次临时要求。
- 当前任务中的明确要求始终高于历史理解。
- 稳定习惯应来自用户明确确认，而不是系统自行宣布。
- 系统可以自动发现和保存候选线索，但从候选经验升级为长期规则时必须让用户确认。
- 记忆应允许被纠正、取代、归档和恢复，而不是通过覆盖或删除伪造一条始终正确的历史。

## 8. 对可能影响结果的理解保持透明

已经确认的稳定习惯可以安静执行，不必每次重复说明。未经确认的暂时理解，或者可能明显改变结果的历史信息，在被使用时应当主动、简短地披露。

**通俗例子：**

Agent 可以说：“我把当前对话判断为开放探索，因此沿用你此前在类似场景中的偏好，暂不收敛成产品定义。如果这次不是这种场景，你可以直接纠正我。”

这让用户在结果偏离以前，就能发现 Agent 对场景的判断是否正确。

**设计含义：**

- 透明不是展示系统调用了多少记忆，而是暴露可能造成意外的影响因素。
- Agent 应说明自己依据了什么、做了什么推断，以及推断适用于什么范围。
- 符合预期的稳定习惯安静执行；可能误解用户的地方主动浮现。

## 9. 信息完整，注意力极简

极简设计不等于删除真实需求，而是让复杂性只在需要时出现。进度、目标、产出、待办、关键判断和会话现场都重要，但不应该同时争夺用户的注意力。

**通俗例子：**

用户重新打开项目时，第一眼只需知道“目前状态”和“下一步”。如果想了解为什么这样决定，再展开关键判断；如果需要追查细节，再进入会话现场和完整产出。信息没有减少，只是按需要逐层出现。

**设计含义：**

- 信息要完整，呈现要有主次。
- 首页不应成为所有模块、指标和通知的堆放场。
- 产品优先帮助用户做出当前决定，再提供深入追溯能力。

## 10. 长期拥有连续性，克制地连接外部工具

长期工作环境不等于包办一切。工作站不需要重做编辑器、终端、Git、任务管理和所有 Agent UI。外部工具已经做得好的部分，应优先连接或复用。

**通俗例子：**

Cursor 已经是成熟编辑器，工作站没有必要再造一个功能较弱的 Cursor。它更应该保证：用户从 Cursor 切换到 Claude Code 或新的 Agent 后，仍然能找到同一项目的目标、历史、产出和关键判断。

**设计含义：**

- 工作站长期拥有用户的工作连续性，不必亲自完成所有工作。
- 新能力进入产品前，要判断它是核心责任，还是更适合交给外部工具。
- 避免为了“一统江山”把产品做成庞大、脆弱、每一项都不够好的超级应用。
- 个人记忆应归用户所有，并且可以检查、纠正、导出和备份；各 Agent 只是按需使用，不应各自持有无法治理的长期副本。

## 11. 设计决策检查表

以后讨论任何模块或功能时，先回答以下问题：

1. 它是否帮助用户更快、更准确地继续工作？
2. 它是否能让今天的工作成为明天更好的起点？
3. 它是否尊重当前任务边界，而不是引入无关信息？
4. 它是否会把暂时理解错误固化为永久规则？
5. 它是否让重要判断和来源保持可追溯、可解释？
6. 它是否必须由工作站亲自完成，还是连接现有工具更合适？
7. 它带来的长期价值，是否高于新增的使用和维护负担？
8. 它是否把内容分类、适用范围、稳定状态和当前相关性混成了一个简单权重？

如果一个想法无法通过这些问题，就不应仅因为“看起来很完整”或“技术上能实现”而进入产品。

## 12. 当前探索边界

截至本文更新时，只有以下两个模块的定位已经足够清楚：

- **Viewer**：关注 Agent 实际产出了什么，以及用户如何查看和管理这些产出。
- **Project Session Map**：关注项目经历了哪些会话，以及会话如何延续、分叉和接续。

启动器、额度查看、Claude Code GUI、统一记忆库、统一知识库、统一插件库和多 Agent 协作都是真实需求或探索方向，但目前不因此自动成为已确认模块。它们仍需接受本文设计哲学的检验。

## 13. 一句话总结

> **以用户的长期工作为中心，让项目、认知与合作经验跨越 Agent 持续演进；保留完整历史，只在正确场景唤起正确经验，以克制、透明和可替换的方式帮助用户持续进步。**
