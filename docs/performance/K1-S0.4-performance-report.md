## Root-cause classification

### Startup

- **C (shell/WebContents creation/load) dominates**: ~67% of process-start→shell-shown
  (window creation, first renderer bootstrap, shell HTML load ≈ 480 ms of 708 ms median).
- **A (Viewer stored-root snapshot/watcher) is the largest controllable critical-path
  blocker**: 64–76 ms at the small stored root, 152–329 ms at the 521-entry root; scales
  with root size and I/O load (203 ms observed under concurrent packaging I/O).
- B rejected: config/quota/migration combined ≈ 50 ms (7%).
- D not on the shell-shown path (engine views connect after `mainWindow.show()`).

### Packaging

- **B (app/asar staging) + A (zip compression) co-dominate**: staging materializes
  ~1.3 GB (98–179 s, cache-dependent), zip compresses it to 416 MB (~130 s, ~40–45% of
  electron-builder time).
- C confirmed as the reason staging is expensive (728 MB asarUnpack closure, mostly
  CloudCLI runtimes), but shrinking it requires externalization — forbidden by scope.
- D minor: npm ci 25.8 s (9% of total), test 13.5 s (5%).

## Implemented changes

1. **Viewer HTTP/control surface decoupled from initial watcher readiness**
   (`src/viewer/server.cjs`):
   - `startServer()` now resolves when the HTTP listener is ready; the initial
     stored-root snapshot/watcher runs in the background (`launchWatcher()`).
   - Correctness guards for #23: `setRoot`/`setConversationContext` still await their
     own watcher baseline; when the root is unchanged they now await the in-flight
     initial baseline (`pendingWatcher`) before returning, so a positively applied
     session root can never silently lose changes. A generation counter discards
     superseded scans; a `closed` flag stops a scan that outlives `close()`.
   - New `whenWatcherReady()` handle for callers/tests that need the baseline.
   - Baseline semantics unchanged: the scan starts at the same moment as before, only
     the server-start promise no longer waits for it.
2. **Opt-in startup profiling seam** (`src/main/main.js`, `src/viewer/server.cjs`):
   `KCC_PROFILE_STARTUP=1` emits `[kcc-profile]` marks for every phase listed in the
   taskbook (process/main start, whenReady, migration, protocol, config, quota, viewer
   listener/snapshot/watcher, window creation, shell loaded, window shown).
3. **Deterministic fast development packaging mode** (`scripts/package-dev.ps1 -Fast`):
   unpacked runnable app in `dist-fast/` via the existing `npm run pack -- fast` path,
   no zip, no separate test phase; frozen source SHA, detached packaging worktree, and
   `build-info.json` provenance (written into `dist-fast/`) are unchanged. The default
   full zip path is untouched.
4. **Validated dependency reuse** (`scripts/package-dev.ps1`): after a successful
   `npm ci`, a stamp (`node_modules/.kcc-dep-stamp`) records SHA-256(package-lock.json)
   + node version + npm version + os/arch. Later runs skip `npm ci` only when the stamp
   matches the frozen source exactly; `-ForceInstall` bypasses. A bare
   "node_modules exists" check is never used.

## After measurements

### Startup (5 runs, same machine/procedure)

In-process ms to `main-window-shown`: 894, 622, 524, 609, 677 →
**median 622 ms (range 524–894)**; wall-to-ready median 1211 ms.

| metric | before | after | change |
|---|---|---|---|
| shown median | 708 ms | 622 ms | **−86 ms / −12.1%** |
| shown range | 651–978 | 524–894 | best run −127 ms / −19.5% |
| viewer server on critical path | 85–95 ms | ~21 ms (listener only) | snapshot/watcher removed |
| viewer snapshot timing | blocks `createMainWindow` | completes at 267–378 ms, hidden under window creation | off critical path |

Large stored root (521 entries / 71 docs / 1.24 MB), after: snapshot 329 ms completed at
522 ms in the background, `main-window-shown` at 717 ms. Under the baseline ordering the
same run would have shown at ≈ 522 + 520 ≈ 1040 ms → **≈ −31% at that root scale**. The
win grows with stored-root size and I/O contention.

Gate note: the 20% median target is not met at the small stored root (−12.1%) because
the baseline is already fast (708 ms median) and 68% of it is Electron window/renderer
creation, which is not reducible without a shell rewrite (explicitly out of scope).
Absolute saving: 86 ms median at ~100-entry roots, ~330 ms at ~500-entry roots, more
under I/O load. The removed blocker was measured, not speculative.

### Packaging

All after-runs used the same deterministic path (frozen source `682a0df…`, same detached
packaging worktree, build-info written per run):

| path | before | after | change |
|---|---|---|---|
| full zip (default), total | 278.5 s (zip 416.3 MB) | 355.8 s (zip 416.3 MB, byte-identical size) | pack-stage variance dominates; see note |
| — full after phases | — | fetch 1.2 · worktree 0.5 · install 1.1 (stamp reuse) · test 18.9 · pack 332.9 | install −25 s vs baseline npm ci |
| fast local iteration (`-Fast`), first run | — | 196.1 s (fetch 1.1 · worktree 0.6 · npm ci 46.5 · pack 146.6) | **−30% vs baseline total** |
| fast local iteration (`-Fast`), stamp reuse | — | **153.4 s** (fetch 2.7 · worktree 0.3 · install 0.8 · pack 148.8) | **−45% vs baseline total** |
| fast artifact | — | `dist-fast/win-unpacked` 1302 MB runnable (exe 215.2 MB) + `build-info.json` | unpacked, no zip |

Honest notes:

- The full zip path is **not** claimed as optimized: its pack stage measured 235.8 s at
  baseline and 332.9 s after — same code path, pure machine/I/O variance (the zip stage
  alone swings ~90–130 s). The only full-path change is stamp-validated install reuse
  (−25.8 s on repeat runs) with the zip artifact unchanged (416.3 MB, same frozen SHA).
- The iteration win is the `-Fast` mode: 278.5 s → 153.4–196.1 s (−30% to −45%), which
  removes the ~130 s zip stage and the test phase from the local loop while keeping
  source freeze, detached worktree, and build-info provenance.
- `npm ci` measured 25.8 s (baseline run) and 46.5 s (fast#1 run) — high variance;
  stamp reuse removes it entirely on repeat runs (0.8–1.1 s validation).

Deterministic proof: both `dist/build-info.json` and `dist-fast/build-info.json` record
`sourceCommit: 682a0df5e2935836e7e4bafae1883b799ca9f103` (verified on disk); packaging
worktree detached and clean at the same SHA for every run; dirty-worktree guard intact.

## Remaining bottlenecks / rejected optimizations

- Startup: window + first-renderer creation (~480 ms, ~68%) is Electron-inherent; the
  ~450–500 ms pre-JS spawn/bootstrap in wall time is likewise fixed cost. Deferring
  engine-view creation was rejected: the shell alone is not "usable", the gain would be
  cosmetic, and it risks tab/IPC regressions.
- Packaging staging (~98–179 s): dominated by materializing the 728 MB asarUnpack
  closure (CloudCLI runtimes). Shrinking it requires dependency externalization —
  out of scope (`STOP PERFORMANCE_ARCHITECTURE_EXPANSION` territory); not attempted.
- Development-only zip `compression=store` probe: inconclusive (electron-builder hit a
  600 s network timeout downloading a tool); not retried because the `-Fast` unpacked
  mode already removes the zip from the iteration loop. Full zip keeps normal
  compression (release semantics untouched).
- npm ci beyond stamp reuse (e.g. cross-worktree caches): not needed; stamp reuse
  already removes the cost on repeat runs.
- Startup profiling seam is permanent but opt-in (env flag); no telemetry added.
