## Product / engineering contract

Development packaging must be deterministic and independent of whichever branch/worktree the user or an Agent currently has open.

The canonical development package source is always the exact fetched `origin/develop/kcc-1.0` SHA.

A package is acceptable only when the user can mechanically answer: **which exact commit produced this package?**

## Required workflow

Implement a Windows PowerShell entry point, preferably:

`scripts/package-dev.ps1`

The script must:

1. locate/validate the repository control root without changing its checked-out branch;
2. run `git fetch origin --prune` (never `git pull`);
3. resolve `origin/develop/kcc-1.0` to an exact SHA;
4. create or safely reuse a dedicated sibling packaging worktree, default:
   `D:\_projects\tools\kcc-workbench-wt-package-dev`;
5. the packaging worktree must be detached at the exact resolved development SHA (it must not become an ordinary user feature branch);
6. if the packaging worktree is registered but dirty, STOP with `PACKAGING_WORKTREE_DIRTY`; do not reset/clean/stash it automatically;
7. if the configured path exists but is not the expected Git worktree, STOP with `PACKAGING_WORKTREE_CONFLICT`;
8. build only inside the packaging worktree;
9. emit package/build output to a predictable output directory that is separate from the user's active feature worktree;
10. write machine-readable build metadata containing at least:
   - `sourceBranch: develop/kcc-1.0`
   - exact `sourceCommit`
   - `builtAt` timestamp
   - package/app version
   - packaging mode (`development`)
11. make the final artifact name or adjacent metadata expose a short source SHA so a bug report can identify the exact build;
12. print a compact final summary with source ref/SHA, worktree path, output path, elapsed time, and artifact file(s).

## Dependency/install behavior

Correctness comes before optimization in this WorkPackage.

Use the repository's existing lockfile/install/build conventions. Do not redesign dependency packaging or aggressively optimize `node_modules` here; #19 owns performance/package-size optimization.

It is acceptable to reuse dependency state in the dedicated packaging worktree only when correctness is proven. If package-lock/install state is not trustworthy, prefer the deterministic install path rather than a clever cache.

Do not modify global npm/NVM state.

## Existing build commands

Current package scripts include:

- `npm test`
- `npm run build` (`electron-builder --win --dir`)
- `npm run dist` (`electron-builder --win`)
- `npm run pack` (`scripts/pack.mjs`)

First inspect `scripts/pack.mjs` and current output conventions. Reuse existing packaging capability where practical instead of creating a second independent packager.

The new PowerShell script is an orchestration/control wrapper around the accepted build path, not a replacement Electron packaging system.

## Safety contract

The script must not:

- switch/checkout/reset the user's control repository;
- touch uncommitted changes in the control repository;
- mutate any feature/fix implementation worktree;
- use the currently checked-out feature branch as the package source;
- `git pull`;
- `git reset --hard` or `git clean` arbitrary worktrees;
- delete a dirty packaging worktree;
- force-update long-lived branches;
- modify `main` or `develop/kcc-1.0` directly.

## Drift / concurrency behavior

The source SHA is frozen once the packaging run resolves it.

If `origin/develop/kcc-1.0` advances while a package is building, the running build must remain tied to the originally resolved SHA. A later run may package the new SHA.

Parallel Agent feature branches must have zero effect on the selected source.

Running the script while the control repo is on a retired branch with uncommitted changes must still package the fetched development SHA and leave that control repo unchanged.

## Build metadata

Prefer a generated file such as:

`dist/build-info.json`

or an equivalent adjacent artifact metadata file.

Do not put secrets, usernames, machine paths, auth state, or environment credentials in build metadata.

A minimal shape:

```json
{
  "sourceBranch": "develop/kcc-1.0",
  "sourceCommit": "<40-char SHA>",
  "sourceCommitShort": "<short SHA>",
  "version": "<package version>",
  "mode": "development",
  "builtAt": "<ISO-8601>"
}
```

## Required acceptance

### A. Dirty control repo isolation

With the ordinary/control repo left on its existing retired/local branch and with its existing uncommitted changes:

- run `package-dev.ps1`;
- prove its branch, status and dirty files are unchanged before/after;
- prove package source SHA equals fetched `origin/develop/kcc-1.0`, not the control repo HEAD.

### B. Feature branch isolation

Create/use a harmless feature worktree whose HEAD differs from develop.

Run packaging and prove the produced metadata still points to exact `origin/develop/kcc-1.0`.

Do not package the feature branch.

### C. Repeatability

Run development packaging twice without develop advancing.

Both runs must report the same source SHA and produce valid packages/build directories from that SHA. Build timestamps may differ.

### D. Development branch advances

Where practical with a controlled docs-only test commit/ref or deterministic seam, prove a subsequent run picks the newly fetched development SHA while a previously completed artifact retains its original source metadata.

Do not create meaningless permanent commits solely for this probe if a seam/test can prove it.

### E. Dirty packaging worktree fail-closed

Create a controlled uncommitted marker in the dedicated packaging worktree and prove the script stops with `PACKAGING_WORKTREE_DIRTY` without deleting/resetting it.

Clean up only the controlled marker after the test.

### F. Build smoke

From the packaging worktree source SHA:

- `npm test` passes;
- the selected existing packaging/build command succeeds;
- expected Electron output exists;
- build metadata matches the exact source SHA.
