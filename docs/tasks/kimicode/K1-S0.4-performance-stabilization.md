## Product goal

Improve the two real KCC 1.0 iteration bottlenecks the user already experiences:

1. **application startup latency** — time from launching KCC to the shell becoming visible/usable;
2. **development update/package turnaround** — time from a known `develop/kcc-1.0` source SHA to a locally usable development build/package.

This is a stabilization/performance WorkPackage, not a shell rewrite, dependency architecture rewrite, updater project, or branding task.

Performance claims must be measured on the user's real Windows machine. Do not optimize by intuition.

## Accepted baseline from #25

Deterministic development packaging is already accepted and merged.

The development source contract is frozen:

- source ref = `origin/develop/kcc-1.0`;
- source SHA is fetched and frozen per run;
- build happens in a dedicated detached packaging worktree;
- control/feature worktrees are not package sources and are not mutated;
- `build-info.json` records exact source provenance.

Do not weaken these guarantees for speed.

Measured full-package baseline from #25:

- total: **~334–418 s**;
- fetch: ~1 s;
- `npm ci`: **~28–62 s**;
- tests: **~13–20 s**;
- `pack` / electron-builder + zip: **~290–338 s** (dominant);
- zip artifact: **~416.3 MB**.

Therefore the first packaging hypothesis to investigate is the `pack` stage, not `git fetch` and not speculative npm caching.

## Confirmed startup critical-path facts at the baseline

At current KCC 1.0 startup, `app.whenReady()` performs several awaited steps before `createMainWindow()`.

Most importantly:

```text
viewerServer = await startViewerServer(...)
...
await createMainWindow()
```

Current Viewer `startServer()` resolves only after an initial `await startWatcher()`.

`startWatcher()` snapshots Viewer documents for the stored root before the server start promise resolves. The Viewer snapshot/watcher code has explicit scan/document/byte limits, but on a nontrivial stored project this work is still on the first-window critical path.

This is a strong hypothesis, not permission to pre-decide the fix. Measure it first.

## Phase 1 — Instrument and establish a reproducible baseline

Before changing behavior, add the narrowest temporary/permanent profiling seam needed to measure startup and packaging.

Prefer opt-in diagnostics such as an environment flag or command-line flag. Do not add telemetry, remote reporting, or user tracking.

### Startup timing points

Measure with a monotonic clock where practical. At minimum capture:

- process/main-module start;
- `app.whenReady()` entered;
- legacy-data migration complete;
- app protocol registration complete;
- workbench config initialization complete;
- quota initialization complete;
- Viewer server initialization start;
- Viewer HTTP listener ready;
- initial Viewer watcher/snapshot ready (separately if possible);
- `createMainWindow()` start;
- shell HTML loaded;
- `mainWindow.show()`;
- first active Agent surface ready enough for normal use where deterministically observable.

The critical metric is **process start -> main shell shown/usable**.

Run multiple baseline launches. Prefer at least 5 comparable runs and report median plus range. Distinguish first/cold-ish run from warm OS-cache runs if they differ materially; do not manufacture a fake "cold boot" by destructive cache operations.

### Viewer root cost

For the stored Viewer root used in the startup probe, capture:

- normalized root identity only if safe for local evidence; do not commit private machine paths;
- scanned entry/document counts;
- snapshot bytes where already measurable;
- initial snapshot duration;
- watcher setup duration.

Use fixture repos as needed for deterministic tests, but include at least one real Windows run representative of normal use.

### Packaging timing decomposition

#25 already provides outer phases. Decompose the dominant `pack` stage enough to answer where the ~5 minutes goes.

At minimum distinguish, where observable:

- electron-builder initialization/config;
- app staging / asar creation;
- asar-unpack copy/materialization;
- native/binary handling;
- zip generation/compression;
- any repeated copying or cleanup.

Also measure:

- full zip package time;
- existing `npm run pack -- fast` / unpacked mode time;
- `dist` zip size;
- unpacked app size;
- largest packaged/unpacked top-level dependency groups or directories.

Do not commit usernames, auth state, or private filesystem paths in evidence.

## Phase 2 — Root-cause classification

Before implementation, state the measured dominant causes.

At minimum classify:

### Startup

A. Viewer stored-root snapshot/watcher is materially blocking first shell;  
B. config/quota initialization dominates;  
C. shell/WebContents creation/load dominates;  
D. Kimi/CloudCLI runtime startup dominates perceived usability after shell show;  
E. another measured cause.

### Packaging

A. zip compression dominates;  
B. app/asar staging dominates;  
C. large `asarUnpack` closure / file count dominates;  
D. dependency install dominates only in some runs;  
E. another measured cause.

Do not implement multiple speculative optimizations before this classification.

## Phase 3 — Startup optimization principles

Use the narrowest repair supported by measurements.

Preferred direction if Viewer initialization is confirmed on the critical path:

1. first shell visibility should not wait for nonessential stored-root Viewer scanning;
2. Viewer HTTP/control surface may become ready before heavy initial snapshot work if the server contract can remain correct;
3. current active Agent session/project must still arm Viewer passively in the background;
4. when a real session/root is positively applied, its watcher/baseline must be correct before changes are silently lost;
5. #23's contract remains mandatory: **opening Viewer is review-only and must not start recording**;
6. startup deferral must not create a race that causes the first Agent task's artifacts to be swallowed or missed.

Possible seams include:

- `src/main/main.js` startup ordering;
- `src/viewer/server.cjs` server-listen vs watcher/snapshot readiness separation;
- a small startup profiling helper/test seam.

Do not introduce a generalized lifecycle framework.

### Startup acceptance

Report baseline vs after on the same machine/procedure.

A change is considered a meaningful win only if it removes a measured critical-path blocker and produces a stable improvement. As a working gate:

- target at least **20% median improvement** in process-start -> shell-shown when baseline is meaningfully slow; or
- if baseline is already too small for a 20% target, show the absolute time saved and explain why further startup work is not worth the complexity.

Do not claim success from a single best run.

## Phase 4 — Development packaging/update optimization principles

The user needs a fast local iteration path, not only a theoretically smaller release artifact.

Preserve #25's deterministic source/worktree/build-info contract.

First measure the already-existing fast unpacked path:

```text
npm run pack -- fast
```

Then choose the smallest useful optimization.

### Allowed directions when supported by data

1. **Deterministic fast development mode**
   - It is acceptable to extend `package-dev.ps1` with a clearly named fast/local mode that still fetches/freezes exact `origin/develop/kcc-1.0` and builds only in the dedicated detached packaging worktree.
   - Fast mode may produce an unpacked runnable app instead of a zip, if that materially shortens the update loop.
   - Fast output must still have exact build provenance metadata.
   - The existing full deterministic zip path must remain available.

2. **Development-only zip/compression tuning**
   - If profiling proves zip compression dominates, it is acceptable to use a development-only electron-builder override/config that trades some artifact size for materially lower local packaging time.
   - Do not globally alter release semantics that future release packaging may need.

3. **Validated dependency reuse**
   - Only if measurement shows `npm ci` is worth optimizing after the dominant pack bottleneck.
   - Any reuse/cache must be mechanically keyed/validated against the exact frozen source's dependency state, at minimum `package-lock.json` content/fingerprint plus relevant runtime/toolchain compatibility.
   - A mere "node_modules exists" check is forbidden.
   - If this becomes complex, do not implement it in this WP; report it as a later optimization.

4. **Safe package-content tightening**
   - Only remove/externalize files when runtime reachability is proven and Kimi/CloudCLI/Viewer regression tests pass.
   - Do not blindly shrink `asarUnpack` based on package names or size.

### Packaging acceptance

Produce before/after measurements using the deterministic development packaging path.

At minimum:

- preserve full zip path and provenance;
- provide a materially faster local iteration path if feasible;
- target **>=30% reduction** in the normal local development turnaround metric selected from the measured baseline, unless profiling proves the dominant cost is not safely reducible inside this architecture;
- if the full zip remains ~5 minutes but a deterministic unpacked/local mode drops iteration time substantially, report both metrics explicitly instead of pretending the full zip was optimized;
- report artifact/unpacked size changes honestly.

## Regression gates

Performance changes must not regress accepted KCC 1.0 behavior.

At minimum preserve:

### Kimi
- local Kimi runtime launch/reuse;
- existing session continuity;
- active session detection.

### CloudCLI
- stable endpoint/origin reuse from #18;
- no unnecessary login caused by performance changes;
- no destructive auth/profile mutation.

### Viewer
- #17 realtime MD/JSON behavior;
- #23 passive session auto-arm;
- fresh session with Viewer never opened during work still records changes;
- session A -> B does not produce empty/stale Viewer state;
- Time Machine remains coherent.

### Shell
- normal Kimi / CloudCLI / Viewer switching;
- no deliberate reload/session destruction just to improve startup.
