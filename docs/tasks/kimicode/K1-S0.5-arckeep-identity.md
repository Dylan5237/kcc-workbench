## Product goal

Keep the accepted KCC 1.0 Electron product/runtime exactly as-is, but replace its **user-visible application identity** with **Arckeep**.

This is an identity swap, not a visual redesign, shell redesign, migration project, updater project, or Arckeep 2.0 resume.

The final user experience should read as:

- application/product name: `Arckeep`;
- window title / shell brand: `Arckeep`;
- Windows packaged executable/zip identity: Arckeep;
- current accepted Arckeep app icon used for packaged app and shell identity;
- Kimi / CloudCLI / Viewer behavior unchanged.

## Accepted source assets

The repository already contains the accepted Arckeep icon assets:

- `arckeep/shell/assets/app-icon.png`
- `arckeep/shell/assets/app.ico`

Use these assets byte-for-byte as the source of truth. Do not redesign, recolor, regenerate, trace, or substitute them.

Because current Electron `build.files` packages `src/**/*` rather than the `arckeep/**` tree, copy the accepted assets into the minimal Electron runtime/build locations required by KCC 1.0 instead of broadening package contents to include the whole frozen Arckeep 2.0 tree.

Prefer semantically named copies such as:

- `src/renderer/assets/arckeep-app-icon.png`
- `src/viewer/public/arckeep-app-icon.png` only if Viewer needs its own static copy;
- `build/icon.ico` replaced with the accepted Arckeep `.ico` bytes, or point the builder at a minimal copied build asset.

Prove copied binary assets match the accepted source hashes.

## Critical compatibility contract — preserve user state

This is the highest-risk part of the task.

Current KCC 1.0 stores Electron application state under the existing KCC `userData` location. That state includes or influences:

- Electron persisted browser/session storage;
- `persist:kimi` partition state;
- quota/browser login state;
- Viewer config / Time Machine state;
- window state;
- workbench config fallback state;
- other local shell settings.

Changing `app.setName('KCC Workbench')` to `app.setName('Arckeep')` can change Electron's default `app.getPath('userData')`.

**The identity change must not silently move to an empty Arckeep profile.**

### Required strategy

Prefer the lowest-risk compatibility design:

> Keep the exact existing production KCC userData path as the stable storage path while changing the visible application name to Arckeep.

In other words, the old storage-directory name may remain as an internal compatibility detail. The user does not need a filesystem rename for this branding task.

Before implementation:

1. measure the current production `app.getPath('userData')` on the baseline build without mutating it;
2. identify which current startup ordering determines that path;
3. implement an explicit compatibility pin so normal Arckeep launches resolve to that exact same path;
4. preserve explicit test/demo/sandbox profile overrides where they already exist; do not break `--demo`, settings sandbox, or controlled `--user-data-dir`/probe behavior if currently supported;
5. keep the existing `Kimi Desktop` legacy migration semantics functional into the stable KCC-compatible destination.

Do **not** create a new copy/move migration from the live KCC profile to an Arckeep profile unless exact-path preservation is proven impossible. If such migration appears necessary, STOP with `IDENTITY_STATE_MIGRATION_REQUIRED` for architecture review before implementing it.

Do not copy, delete, reset, rewrite, or clean real auth/profile data during automated tests.

## Identity changes in scope

At minimum inspect and update the current user-visible identity surfaces:

### Electron / package

- `package.json` `build.productName` -> `Arckeep`;
- packaged artifact name -> preferably `Arckeep-${version}-${arch}.${ext}`;
- Windows icon -> accepted Arckeep icon;
- `app.setName(...)` -> `Arckeep`, while preserving the existing userData path contract;
- main window title -> `Arckeep`;
- fatal/error-box product wording where it identifies the app -> `Arckeep`.

### Shell

- user-visible `KCC Workbench` brand/title -> `Arckeep`;
- current shell brand icon -> accepted Arckeep app icon;
- keep layout, spacing, navigation, colors and interaction unchanged except for dimensions strictly required by the new name/icon.

### Viewer

Only replace KCC-specific identity where the Viewer itself currently presents the enclosing application brand. Do not rename generic `Viewer`, `Time Machine`, Kimi, Claude, Codex, CloudCLI, or technical artifact concepts to Arckeep.

### Packaging/docs directly tied to usage

Update current packaging usage/docs where they refer to the generated KCC artifact name or app identity.

Do not rewrite historical project documents, old ADR evidence, old taskbooks, issue history, branch names, or old release notes merely to remove the letters `KCC`.

## Deliberately stable internal identifiers

## Required acceptance

### A. Production userData path preservation

Prove, using the same normal profile semantics:

- baseline KCC `app.getPath('userData')` = X;
- Arckeep candidate `app.getPath('userData')` = X;
- exact normalized path equality, not merely equivalent contents.

No real profile files may be destructively changed for this proof.

### B. Existing state continuity

Using a safe controlled profile representative of the current KCC state, seed and verify at least:

- a shell/workbench setting;
- window-state/config data;
- Viewer stored root/config or equivalent non-secret persisted state;
- Electron persisted partition/session state where safely testable.

Launch the Arckeep candidate against the same profile and prove the state remains readable without migration/reset.

For real user auth/session continuity, prefer path/partition invariants plus non-destructive normal smoke. Do not inspect or expose secret cookie/token values.

### C. Kimi continuity

Normal Kimi surface still loads/reuses its runtime/session behavior. No forced login, profile reset, session destruction or workspace reset caused by branding.

### D. CloudCLI continuity

Preserve #18 endpoint/origin behavior and existing local auth continuity. No destructive auth/profile action.

### E. Viewer continuity

Preserve #17 realtime behavior and #23 passive auto-arm. A fresh session must still record without requiring the Viewer to be opened during work.

### F. Packaged identity

Using deterministic packaging from the accepted development path:

- package/build source provenance still comes from exact `origin/develop/kcc-1.0`;
- artifact identifies as Arckeep;
- executable/window title identifies as Arckeep;
- accepted Arckeep icon bytes are used by the packaged Windows build;
- `build-info.json` remains correct.

### G. Visual human gate

Agent must not perform screenshot-based visual acceptance.

After machine checks pass, request HUMAN_ACTION only if needed for the final visible check. The user can provide a screenshot of the running candidate/taskbar/window; ChatGPT performs visual acceptance.

The human gate should check only identity correctness, not redesign:

- Arckeep name visible where expected;
- Arckeep icon appears correctly;
- no accidental KCC logo/text remains in primary shell identity;
- layout was not redesigned.
