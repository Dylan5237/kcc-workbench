## Goal

Remove unnecessary repeated authentication friction when the user switches to CloudCLI / Claude Code or restarts KCC 1.0.

This task means **persist and reuse legitimate local authenticated state**. It does **not** mean bypassing provider security, copying credentials, or storing plaintext passwords/tokens in KCC.

The user should authenticate once when genuinely required, then normal KCC restarts should reuse that state.

## Current facts

At the baseline:

- KCC bundles `@cloudcli-ai/cloudcli@^1.37.1` and launches its server through the user's system Node.
- `CloudCliService` inherits `process.env` and currently adds `SERVER_PORT`, `HOST`, `NO_OPEN`, and `PYTHONUTF8`.
- It does not explicitly pin `DATABASE_PATH`, `CLAUDE_CONFIG_DIR`, `CLAUDE_CLI_PATH`, HOME, or USERPROFILE.
- CloudCLI supports a persistent authentication database via `DATABASE_PATH`; its documented default is user-scoped (`~/.cloudcli/auth.db`).
- KCC prefers port 42100 but scans upward if that port is occupied.
- Browser/session state is origin-sensitive, so `127.0.0.1:42100` and `127.0.0.1:42101` are distinct web origins.
- KCC's CloudCLI `WebContentsView` must remain persistent across ordinary engine switching.

These are investigation facts, not a preselected root cause.

## First requirement: identify which login is repeating

Before changing code, reproduce on Windows and classify the prompt precisely:

1. **CloudCLI local UI authentication** — CloudCLI's own local web/JWT/account gate.
2. **Claude Code provider authentication** — the underlying `claude` CLI / Anthropic provider state.
3. **Both**.

Capture enough evidence to distinguish the layer without exposing secrets. Redact tokens, cookies, authorization headers, account identifiers, and credential values from logs/evidence.

Inspect at minimum:

- `cloudcli status` / upstream-supported config for the exact installed version;
- resolved auth/database path used when KCC launches CloudCLI;
- HOME / USERPROFILE semantics inherited by the spawned system Node process;
- whether the locally installed `claude` command is already authenticated outside KCC;
- whether CloudCLI invokes that same user-scoped Claude state;
- CloudCLI Web UI storage/cookie behavior across KCC restart;
- actual port/origin across launches;
- behavior when 42100 is occupied;
- whether a stable upstream-supported `DATABASE_PATH` or related configuration solves the problem.

Do not assume the database path or port is the cause until reproduced.

## Preferred repair order

Use the narrowest upstream-supported seam that solves the reproduced problem.

### A. Stable user-scoped CloudCLI auth state

If CloudCLI is accidentally resolving its auth DB somewhere transient or app-relative, explicitly point it to the normal user-scoped CloudCLI data location supported by the installed CloudCLI version.

Prefer a path independent of KCC/Arckeep `productName` so the later #20 identity swap cannot silently destroy auth continuity.

Do not copy existing database contents unless required and explicitly justified. Prefer reusing the existing canonical CloudCLI location.

### B. Existing Claude CLI auth state

If the repeated prompt is provider authentication, prove whether KCC's spawned CloudCLI sees the same authenticated `claude` CLI configuration as the user's normal terminal.

Preserve/inherit the user's normal HOME / USERPROFILE / supported Claude config location. Do not read or duplicate secret values into KCC config.

Only set `CLAUDE_CONFIG_DIR` or `CLAUDE_CLI_PATH` if the installed tooling/upstream behavior proves it is necessary.

### C. Web origin / port continuity

If CloudCLI local UI auth is stored per origin and repeated login is caused by port drift, solve it with the smallest safe lifecycle change.

Preferred choices, in order:

1. retain/reuse a stable known CloudCLI port when available;
2. if the preferred port is occupied, positively verify whether the occupant is the expected compatible local CloudCLI before any attach/reuse;
3. otherwise choose a deterministic persisted KCC CloudCLI port only if needed.

Never attach to or trust an arbitrary process solely because a port is open.

Do not disable authentication by undocumented patching just to avoid a login screen.

## Human authentication boundary

If a real login is genuinely required during verification, do not request credentials, tokens, cookies, API keys, or passwords from the user.

STOP with:

`HUMAN_ACTION_CLOUDCLI_LOGIN`

and tell the user exactly which local KCC/CloudCLI screen to complete once. Resume testing after the user confirms login is complete.

## Required behavior

After the minimal repair:

1. user authenticates once if needed;
2. use CloudCLI / Claude Code successfully;
3. close KCC normally;
4. reopen KCC and switch to CloudCLI — no unnecessary login prompt;
5. close/reopen KCC a second time — still no unnecessary login prompt;
6. the locally authenticated Claude CLI remains usable and is reused where upstream CloudCLI supports it;
7. Kimi / Viewer switching and CloudCLI session discovery remain intact.

## Required failure / edge checks

- Verify behavior with the preferred port available.
- Deliberately occupy the preferred port with a non-CloudCLI listener and prove KCC does not falsely attach to it.
- If the repair relies on a stable origin, document what happens under genuine port conflict and whether one re-auth is still necessary after an origin change.
- Restarting CloudCLI inside one KCC process must not erase the persistent auth state.

## Security / ownership rules

Forbidden:

- plaintext credentials in repository, settings, logs, environment snapshots, test fixtures, or task evidence;
- copying browser cookies/JWTs into KCC source/config;
- provider-auth bypasses;
- patching/forking CloudCLI without an architecture STOP;
- broad process discovery / `taskkill` by image name;
- changing Electron framework or migrating to cdesktop;
- unrelated startup/package optimizations (#19);
- branding/app-name changes (#20).

If the installed CloudCLI version cannot provide a stable supported auth seam and a fork/patch appears necessary:

`STOP CLOUDCLI_AUTH_UPSTREAM_LIMIT`

with evidence and the smallest proposed exception. Do not implement the fork.
