## 1. v0.1 到 v0.2 变化了什么

| 主题 | v0.1 | v0.2 变化 | 依据 |
| --- | --- | --- | --- |
| 项目恢复视图 | 候选，形态待定 | 确认为"项目空间"，开放空间结构，无固化流程 | 用户否定看板版和流程版原型 |
| 系统建议 | "系统建议下一步" | 改为"可能值得继续的事"，系统推测与用户待办混排，平等呈现，不是指令 | 用户不希望被系统指挥 |
| 视觉方向 | 未定 | A 方向"纸感人文"定调：暖白纸底、衬线标题、墨色文字、琥珀点缀 | 用户在 A/B 对比中选择 A |
| 信息布局 | 未定 | 项目空间用双栏：左栏动态信息（继续的事 + 关键判断），右栏稳定信息（产出 + 会话现场 + 启动区）；不允许出现滚动条 | 用户明确要求"别让我下滑" |
| Viewer 集成 | 已确认模块，未定形态 | 产出屏 = 完整 Viewer（文件树 / 本轮产物 / 时间机器 / 三模式 / diff / Git 分叉），保留 v1 全部交互能力 | 用户要求"保持 viewer 的完整功能" |
| Agent 接入 | 原则性描述 | 确认"大块原生 + 窄条项目侧轨"的接入态形态 | 原型验证 |
| Session Map | 已确认模块，分叉语义未决 | 分叉节点视觉上"虚线 + 半透明"，点击后详情标注"（推测）"；废弃分叉的操作暂不实现 | 原型探索，避免固化未验证交互 |

## 2. 视觉语言（A 方向 · 纸感人文）

### 2.1 设计基调

像一本安静的工作笔记，不是工具面板。

- 底色：暖白纸感 `#faf7f2`，侧栏略深 `#f4efe7`，内容面 `#fffdf9`
- 文字：墨色 `#2b2620` 主，`#6b6053` 次，`#9a8f7e` 三级，`#c4b9a6` 四级
- 边线：`#e6ddd0`（主分隔）、`#efe7db`（次分隔）、`#d9cfbf`（控件边框）
- 点缀：琥珀 `#c4a35a`（系统推测的圆点、选中下划线、主动作按钮）
- 状态色：绿 `#5c7a52`（实时监听 / 新增）、红 `#a05a45`（删除）
- 字体：标题和关键句用衬线（Songti SC / Noto Serif SC），正文用无衬线（Segoe UI / Microsoft YaHei），文件名和代码用等宽（Consolas / ui-monospace）

### 2.2 组件风格

- 圆角：侧栏项和内容块 6px，按钮 16px（胶囊），Viewer 容器 8px
- 按钮：次要 = 白底描边，主要 = 墨底白字，主动作 = 琥珀底白字
- 选中态：侧栏项 = 白底 + 柔和阴影，Viewer 列表项 = 左侧 3px 琥珀条 + 白底
- 系统推测：琥珀色圆点 + 灰色来源标注；用户自己写的：灰色圆点 + "你自己写的"来源
- 当前判断：墨底白字标签；已取代判断：浅褐底灰字标签，内容本身变灰

### 2.3 布局约束

- **不允许出现页面级滚动条。** 所有信息在一屏内呈现，桌面端（1920×1080 及以上）必须完整可见。
- 项目空间用双栏，左栏放动态信息（可能值得继续的事、关键判断），右栏放稳定信息（最近产出、会话现场、启动区）。
- Viewer 屏内部列表可以滚动（文件多），但页面本身不滚动。

## 3. 四屏规格

### 3.1 屏 1 · 项目空间（默认落点）

**信息结构与排版**（自上而下）：

1. 标题行：项目名，衬线 12px，字距 .28em，灰字
2. 开场白：`[你确认的] 08-27 16:02 更新` 标签行 + 一句话衬线 20px（当前状态）
3. 双栏区域：
   - 左栏
     - "可能值得继续的事"（系统推测 + 用户待办混排，条目：圆点 + 文本 + 来源）
     - "关键判断"（当前 / 已取代标签 + 判断文本 + 来源行）
   - 右栏
     - "最近产出"（等宽文件名 + 元信息，最多显示 6 条）
     - "会话现场"（最后两条对话引用，竖线左框）
     - "继续"启动区（agent 胶囊按钮 + 琥珀"开始"按钮）

**数据来源**：

| 信息 | 来源 | 说明 |
| --- | --- | --- |
| 当前状态 | 用户确认的项目状态 | 只能由用户确认或改写，系统不自动更新 |
| 可能值得继续的事 | 系统从最近会话提取候选 + 用户手动添加 | 系统推测需标注来源；用户条目用灰点区分 |
| 关键判断 | 用户确认的设计决策 + 历史版本 | 来源必须可追溯；被取代的保留可查但不支配现在 |
| 最近产出 | 真实工作目录 + Git | 按修改时间排序，以文件系统为准 |
| 会话现场 | 最近一次 agent 会话的末尾片段 | 摘要只是索引，可跳转原始会话 |

**用户可执行动作**：

- 点击"可能值得继续的事"某条 → 将其作为接续点，高亮后可点"开始"
- 点击 agent 胶囊 → 切换（互斥），项目和上下文不变
- 点击"开始" → 弹出上下文勾选面板（默认最小相关），确认后进入接入态
- 添加自定义待办（原型未实现，v0.2 开发包含）

**空态**：新项目无任何信息时，开场白显示"这是一个新项目，还没有工作记录"，其余字段显示引导文案。

### 3.2 屏 2 · Session Map

**结构**：画布区（节点 + 连线）+ 详情区（选中节点信息）+ 启动区。

**节点数据**：

| 字段 | 说明 |
| --- | --- |
| name | 会话标题 |
| agent | 参与的 agent（Codex / Claude Code / Kimi Code 等） |
| time | 时间 |
| status | confirmed（实线）/ tentative（虚线半透明）/ fork（分叉） |
| summary | 会话摘要，由用户确认 |
| source | 摘要来源（哪次会话、谁确认） |

**分叉语义（v0.2 边界）**：分叉节点显示为虚线 + 半透明，详情中标注"（推测）"。点击分叉不改变任何状态，仅显示详情。确认废弃、合并等操作暂不实现，避免固化未验证的交互。

**用户可执行动作**：

- 点击节点 → 切换选中，详情区更新
- 从选中的经历继续 → agent 选择 + 开始

### 3.3 屏 3 · 产出（完整 Viewer）

这一屏继承 v1 Viewer 的全部已验证能力，视觉套用 A 方向。

**结构**：

1. 工具栏：标题"产出" + 模式切换（自动 / 开发 / 运行）+ 实时监听指示
2. 侧栏 tabs：文件 / 本轮产物 / 时间机器
3. 主体：左侧列表（270px）+ 右侧内容区，底部固定文案"以真实工作目录为准 · 不做第二份事实"

**模式语义**（继承 v1）：

| 模式 | 显示范围 |
| --- | --- |
| 自动 | 按会话性质推断 |
| 开发 | 全量文件 |
| 运行 | 人类可读产物（.md / .html / .json / .mmd） |

**三个侧栏的能力**（继承 v1）：

- **文件**：过滤输入框 + 文件列表（等宽文件名 + 类型徽章 + 修改时间 + 大小）。点击文件在右侧打开预览。HTML 文件提供"安全预览 / 源文件"切换；Markdown 渲染排版。
- **本轮产物**：本次会话产生的文件变化（新增 / 修改 / 删除 + diff 行数 + 时间）。点击在右侧显示带行号的 diff（+绿 −红）。
- **时间机器**：检查点列表（时间轴圆点样式，时间 + Git 分支 + 文件数）。点击检查点 → 右上角"从这里继续（Git 分叉）"按钮，仅在用户确认后执行 Git worktree 创建。

**Agent 产出回传**：agent 会话结束后，本轮产物自动刷新到"本轮产物"侧栏，会话结束事件同时更新项目空间的"最近产出"。用户不需要手动复制。

### 3.4 屏 4 · Kimi 接入态

**结构**：左侧大块 = agent 原生界面（Electron `WebContentsView` 嵌入），右侧窄条（250px）= Arckeep 项目侧轨。

**接入 ≠ 改造**：agent 的按钮、会话列表、输入框保持原样，Arckeep 不重绘、不搬运、不统一聊天界面。

**右侧侧轨的四块信息**：

| 块 | 内容 | 数据来源 |
| --- | --- | --- |
| 本项目 | 目录、接续点、携带上下文数 | Arckeep 项目数据 |
| 会话状态 | 进行中 / 已结束、来自哪个 agent、开始时间 | agent 会话 API（Kimi 已验收） |
| 文件变化 | 本次会话期间的真实文件变化（文件名 + 新增/修改/行数） | 工作目录监控 + Git diff |
| 接回项目 | "会话结束 · 回到项目"按钮 | 用户点击后触发摘要回流 + 产出刷新 |

**降级策略**：如果 agent 的会话 API 不可用（或该 agent 尚未适配），会话状态块显示"该 agent 的会话未接入"，文件变化仍然可用（文件系统监控不依赖 agent）。

## 4. 数据模型（v0.2 最小集）

### 4.1 Project

```text
Project {
  id: string              // 稳定标识，本地目录路径的规范化形式
  name: string            // 显示名
  rootPath: string        // 工作目录绝对路径
  currentStatus: {        // 开场白
    text: string
    confirmedBy: 'user'
    updatedAt: timestamp
  }
  nextItems: [            // 可能值得继续的事
    { id, text, source: 'system'|'user', sourceRef: string, isSystemGuess: boolean }
  ]
  decisions: [            // 关键判断
    { id, text, status: 'current'|'superseded', source: string, confirmedAt: timestamp }
  ]
  artifacts: [string]     // 最近产出，从文件系统读取，不复制
  lastSession: {          // 会话现场
    agent: string, endedAt: timestamp, excerpt: [{speaker, text}]
  }
}
```

### 4.2 SessionNode

```text
SessionNode {
  id: string
  projectId: string
  agent: string
  time: timestamp
  status: 'confirmed' | 'tentative' | 'fork'
  summary: string
  source: string
  parentId?: string       // 接续自哪个节点
}
```

### 4.3 数据与事实边界（继承 v0.1 §11）

- 项目文件以真实工作目录为准，工作站不复制为第二份事实
- Git 历史以仓库为准
- agent 原始会话由其原生载体保留，工作站只存索引、关系和必要快照
- 系统生成的摘要和判断必须标注"系统理解"并保留来源

## 5. Agent 接入协议

### 5.1 最小共同要求（继承 v0.1 §12）

一个 agent 若要参与项目，理想上提供：当前项目目录、会话身份和时间、产出或文件变化线索、可供恢复的会话入口、接收相关项目上下文的方式。

### 5.2 接入深度分级

| 级别 | 能力 | 典型 agent |
| --- | --- | --- |
| L1 · 登记 | 只显示项目入口，不读会话 | Cursor |
| L2 · 目录透传 | 项目目录传给 agent，文件变化可监控 | DSH |
| L3 · 会话回读 | 会话身份、时间、摘要可读回 Session Map | Kimi Code（已验收）、Claude Code、Codex |
| L4 · 产出对账 | 会话结束自动触发本轮产物刷新和摘要回流 | 目标状态，依赖 L3 |

### 5.3 Kimi 接入（已验证路径）

v1 已验收 Kimi Code Web 嵌入 + 会话 API 目录解析。v0.2 延续这条路径，增加：会话结束事件触发回流、文件变化与会话关联。

### 5.4 Claude Code / Codex 接入

v1 已通过 CloudCLI 支持这两个 agent 的启动和 Viewer 目录跟随。v0.2 将它们的会话索引读入 Session Map（jsonl 活动作为降级来源），接入态复用同一形态。

## 6. 从 v1 演进的路径

不推倒重来，分三步渐进：

| 阶段 | 内容 | 验收标准 |
| --- | --- | --- |
| 1 · 项目空间落地 | v1 打开后不再直接进入引擎列表，而是先进入项目空间；选中项目后可进入任一 agent | 用户能以"项目"为入口开始工作 |
| 2 · Viewer 集成 | v1 Viewer 嵌入产出屏，A 视觉套用，能力不缩减 | 产出屏三个侧栏 + 模式切换 + diff + 时间机器全部可用 |
| 3 · Session Map 最小模型 | 先只记录本地可读的会话关系（v1 已接的 agent），分叉语义按 §3.2 边界实现 | 能看到项目经历过的会话脉络，能从某个节点继续 |

每阶段独立可验收，不要求一次性交付。现有 Kimi / CloudCLI / Viewer / 时间机器能力全程保持可用。

## 7. 开发边界（明确不做）

- 不做完整记忆库、知识库、插件市场（候选能力，未确认）
- 不做 agent 界面的统一改写
- 不做 Session Map 分叉的废弃/合并操作（语义未验证）
- 不做多 Agent 协作编排（管理者-执行者模式未确认为最佳实践）
- 不做移动端、Web 端（Windows 桌面优先）
- 不做云端同步（本地优先，v0.2 不引入）

## 8. 验收标准

本文 + 完整视觉稿交付后，以下问题应该都能回答"是"：

1. 用户能否不看说明就知道打开应用后第一眼该看什么？（项目空间开场白）
2. 用户能否分辨系统推测和自己写的待办？（圆点颜色 + 来源标注）
3. 用户能否追溯任何一条关键判断的来源？（来源行）
4. 用户能否核查 agent 说"完成"的实际产出？（本轮产物 diff）
5. 用户能否回到某个历史时间点继续工作？（时间机器 + Git 分叉）
6. 用户能否在不滚动的情况下看到项目空间的全部信息？（双栏布局 + 密度控制）
7. agent 的原生界面是否保持原样，Arckeep 是否只在侧轨提供项目上下文？（接入态比例）
8. 视觉稿和文档是否用同一套视觉语言，可以直接交给开发者开工？

## 11. 总结

Arckeep v0.2 完成了从产品哲学到可开发规格的完整落地：项目空间取代固化流程，A 方向纸感人文取代灰阶线框，完整 Viewer 保留产出核查能力，接入态确立"大块原生 + 窄条项目侧轨"的克制模式。

下一步是按 §6 的三阶段路径，在现有 v1 基础上渐进实现。

> **工作站长期拥有工作连续性，Agent 只提供不断变化的工作能力。**
